# Outcome 产品设计原理与洞察

版本 0.1 · 更新：2026-10-14 · 配套 [SPEC.md](SPEC.md)、[DDD.md](DDD.md)、[ROADMAP.md](ROADMAP.md)

本文回答一个问题：**为什么 Outcome 是现在这个样子**。每条设计都对应一个被反复观察到的失败模式；改变设计即意味着接受另一种失败。实现团队与评审方应先读本文，再读规范。

## 1. 我们面对的真实问题

企业引入数字员工（Agent）后，普遍陷入三类困境：

1. **价值说不清**：汇报口径是"运行了多少次任务、调用了多少 token"，但业务负责人问的是"到底省了多少钱、谁认可的"。缺少以业务验收为锚的价值归因，预算评审过不了，失败项目也无法及时止损。
2. **质量管不住**：自动评分高的方案上线后返工更多；评测集被自己人"刷分"；一次实验宣称的提升，换个数据集就消失。质量数据没有制衡机制，等于没有数据。
3. **改进不可信**：问题发现了、样本采了、实验跑了，但结论基于不对齐的输入、有偏的抽样或事后变动的口径——改进成了叙事，不是事实。

Outcome 的全部设计，都是让这三件事在证据层面成立，而不是在汇报层面成立。

## 2. 六条不可妥协的设计立场

| 立场 | 内容 | 它挡住了什么失败 |
| --- | --- | --- |
| 业务验收是唯一价值锚点 | 运行成功、评分通过都不等于价值；只有宿主授权用户的验收判定才计入成果 | 防止"跑通了=有收益"的虚假繁荣 |
| 事实、评分、价值三权分离 | 任务事实归宿主事件；质量评分归评测体系；价值归因归基准与报告——互不写入 | 防止质量模块把业务状态改成"通过"，防止分数污染经营口径 |
| 未知就是未知 | 成本缺失不补零、零基准不算率、缺样本不外推、证据不足标假设 | 防止用漂亮的比率掩盖数据残缺，保住财务与审计可信度 |
| 历史不可改写 | 判定、基准版本、评测版本、实验输入、报告全部冻结或留链 | 防止"口径优化"篡改已发生的结论，让每份报告可被事后复核 |
| 低侵入，不做第二个执行框架 | 通过事件契约接入既有业务与 Agent 系统，Outcome 只做治理与归因 | 防止平台建设吞掉价值验证本身，防止绑定单一技术栈 |
| 制衡优先于自动化 | 独立性、校准与问责是硬门禁；吞吐不足时先让 Agent 扩大覆盖，人收敛到金标准与仲裁，而不是砍掉制衡换速度 | 防止"效率"成为拆掉地基的理由，也防止"必须人工"成为规模化的天花板 |

## 3. 关键设计决策：原因与洞察

### 3.1 为什么以"任务-尝试-成果-判定"建模，而不是以"会话/调用"建模

**决策**：Task / Attempt / ArtifactVersion / Verdict 四元结构；重试新增尝试且失败投入保留；验收必须匹配意图版本、标准版本与成果版本。

**原因**：调用级数据回答不了业务问题。一次任务可能多次重试、多个 Agent、多份成果，业务方只验收最终那份。以调用为单位统计，会把失败尝试藏进平均值，也会把一次验收拆成 N 份"成果"。

**洞察**：数字员工的价值核算单位必须与人类员工一致——**一件事、一次交付、一次验收**。口径与人类对齐，业务方才能用直觉校验数字；口径不一致，任何节省率都会在第一次质询时崩塌。

### 3.2 为什么业务状态只能由宿主事件改变

**决策**：Outcome 内任何质量评分、复核结论、实验结果 MUST NOT 改写任务业务状态；状态权威在宿主。

**原因**：一旦平台可以"点通过"，它就成为第二个权威来源。两边状态漂移时，没人知道该信谁——这正是所有工单系统与业务系统对接失败的经典模式。

**洞察**：**治理平台的可信度来自"不拥有权力"**。Outcome 敢于把验收权完全留在宿主，反而使它的价值报告具备仲裁力：它不决定业务，它证明业务。这是刻意的权力克制，不是功能缺失。

### 3.3 为什么成本口径如此苛刻（不补零、不算零率、失败入总账）

**决策**：未知成本不补零；零基准不计算节省率；失败、取消、接入、平台、治理的已知投入全部进入经营总成本；可比子集收益与部署整体净收益分别报告，禁止外推。

**原因**：省钱的幻觉几乎都来自分母处理——把缺失当零、把不可比任务剔出分母、把失败投入踢出成本、再用可比子集的高节省率外推全量。每一条"美化"单独看都无害，叠加起来就是一份过不了 CFO 质询的报告。

**洞察**：**价值报告的第一读者是怀疑者，不是拥护者**。设计时假设读者会逐项质询每个数字的来源，那么系统就必须能当场回答"这个分母里有什么、缺什么、为什么缺"。诚实的缺失说明（覆盖了多少、缺在哪、能否补）比一个虚高的节省率更有商业说服力——因为它可被审计，因而可被决策采用。

### 3.4 为什么标注、复核、仲裁必须分离——以及为什么这不等于"必须由人执行"

**决策**：标签提交与复核必须由相互独立的主体完成，分歧由第三方仲裁；独立性约束的是执行谱系与激励关系（不共享执行配置、提示链与收益信号），不限制主体是人还是 Agent。复核 Agent 必须满足：谱系隔离、可问责身份、金标准校准有效、抗女巫克隆、防注入（无真值写入与状态变更权限）。高风险范围、分歧仲裁与发布门禁强制保留人工核验路径，并记录人工核验覆盖率。

**原因**：评测集是整个改进体系的地基。自己（或自己的同谱系副本）标、自己复核，短期内数据"变好"，长期是地基被腐蚀——后续所有实验结论都建立在被污染的标签上，且污染不可见。但另一端的失败同样真实：Agent 产量上升后，要求人工全量标注复核，治理闭环会先于业务死于吞吐瓶颈，结果要么积压、要么"默契放水"——两者都回到地基腐蚀。

**洞察**：**制衡的对象是利益与信息，不是物种**。人工复核之所以有效，不是因为人更聪明，而是因为人与执行者的激励和信息流分离——这个分离可以用制度在 Agent 身上重建（谱系+校准+问责+抽样仲裁），也可以被廉价的克隆实例摧毁（女巫问题）。所以正确解不是"取消人工"也不是"必须人工"，而是：**Agent 做全量初审扩覆盖，人做金标准、校准审计、仲裁与最终问责收精度**；独立性是可审计的资格状态，不是岗位描述。

### 3.5 为什么实验必须冻结输入才允许比较

**决策**：同数据/样本/标准才允许逐样本比较与提升排名；不兼容实验只能描述性并列；小样本不得宣称稳定结论；结论须独立审核。

**原因**：Agent 方案的"提升"极容易被输入差异、标准漂移、执行版本变化稀释成噪声。业界常见的失败模式是：A 实验用旧样本、B 实验用新样本，然后汇报"+18%"。

**洞察**：**可比性是结论的前置条件，不是注意事项**。产品上把"可比性提示"放在比较动作之前（而不是报告脚注），是把统计纪律固化进交互流程——用户想犯错，界面先拦住。这与 Symphony"策略与证据随版本走"的思想同源：**口径版本化，结论才可复现**。

### 3.6 为什么在线验证保留"未入选"记录、拒绝风险样本代表总体

**决策**：抽样决策（含未入选）全部留痕并记录入选概率；风险抽样与随机抽样分别解释；风险样本均值不得代表总体；失败投入照记。

**原因**：在线验证最常见的自欺是：只看触发了评测的高风险样本，得出"质量很差"或"改好后大幅提升"的结论——而这些样本既不是随机的，入选概率也未记录，无法还原总体。

**洞察**：**抽样偏差无法事后补救，只能事前留证**。产品选择"多存一份决策记录"而非"多算一个漂亮指标"，因为前者让结论在数学上可辩护。这是用存储成本购买结论可信度，且只在决策时刻付一次成本。

### 3.7 为什么在线结果只能回流为待标注草稿

**决策**：在线执行结果可回流评测集，但状态只能是"待标注草稿"，必须经过独立标注与复核才能成为真值。

**原因**：如果执行结果自动成为真值，自动评分就会闭环自证——系统用自己产生的数据证明自己正确。这是模型评估领域公认的自杀式设计。

**洞察**：**真值只能来自被制衡的判断，执行者不能既当运动员又当守门员**。机器（含执行 Agent 自己的评分）只能产生候选；候选要成为真值，必须经过独立谱系的复核与校准门禁——复核主体可以是校准过的 Agent，但"独立"这个属性一寸都不能让。这条约束牺牲了"全自动闭环"的演示亮点，换回评测集的长期有效性。

### 3.8 为什么报告要冻结，而不是实时刷新

**决策**：报告在截点冻结范围、公式版本、基准与任务快照；后续基准变更不影响已发布报告。

**原因**：实时报告在口径调整的瞬间就失去历史可比性。上季度的结论如果随本周配置变化而改写，管理层将无法基于任何报告做跨期决策。

**洞察**：**报告是法律文书，不是仪表盘**。仪表盘回答"现在怎样"，报告回答"当时依据什么得出什么结论"。把两者混为一谈，是 BI 类产品在治理场景中水土不服的根源。Outcome 选择牺牲"实时性"这个卖点，购买"每份报告终身可复核"。

### 3.9 为什么洞察必须分级（事实/假设/已验证）

**决策**：证据缺失或过期不得显示为已验证；相关性不得写为因果；自然语言摘要不得补造数字；未经线上复测不得宣称真实改进。

**原因**：数据分析产品的通病是把"发现了相关"直接写成"原因就是它"。一旦 LLM 摘要介入，还会额外产生数字幻觉。两者叠加，洞察页会变成最高级的误导渠道——因为它长得最像结论。

**洞察**：**洞察的产品价值不在于数量，而在于分级可信**。一个标注为"假设、待验证、负责人 X、验证方案 Y"的条目，比十条"已验证"更有组织价值——因为它驱动下一步动作，而假结论只会终止思考。分级状态机把"诚实"做成了工作流，而不是免责声明。

### 3.10 为什么接入只做事件契约 + 对账，不做全托管执行

**决策**：通过版本化事件接入宿主事实；提供 fetch 对账操作；不重建 Agent 执行框架、不替代宿主验收、不统一全企业流程。

**原因**：执行框架是红海且高度异构，Outcome 若绑定执行层，会失去跨框架的治理中立性，也会把项目拖入集成泥潭（每个客户执行栈都不同）。而"价值证据"这一层恰好是通用的、空白的。

**洞察**：**选战场时选"所有玩家都绕不开、但没人认真做"的层**。执行层人人有，验收与归因层人人缺。Symphony 选择向下做执行编排（它的护城河是运行时），Outcome 选择向上做证据治理（护城河是口径与制衡）。两条路线互补而非竞争：Outcome 未来可把 Symphony 类编排系统的运行事实作为 Attempt 来源之一。

### 3.11 为什么权限上"管理员不自动拥有验收权"

**决策**：平台管理员不自动继承宿主业务验收权；最后管理员保护；撤销即刻生效；服务端全链路校验。

**原因**：治理平台天然吸引"给管理员开后门"的妥协——方便，但会破坏第 3.2 条的权力克制：平台管理员若能验收任务，价值报告就不再独立于平台方。

**洞察**：**权限设计要保护的是"证据生产过程的独立性"**，不只是数据安全。这与新闻编辑部保护信源、审计所隔离咨询业务是同一原理：生产结论的人不能同时拥有改变事实的权力。

### 3.12 为什么规范、原型、验证脚本三件套一起发布

**决策**：SPEC 定义 MUST 行为；index.html 原型展示流程；scripts 验证领域逻辑（幂等、冻结、权限、算例）；三者互相引用、编号对齐（TC 矩阵）。

**原因**：纯规范会被实现方各自解读，纯原型会被当成"页面参考"糊弄逻辑。规范里写"未知不补零"，原型里必须真的不补零，验证脚本里必须有"基准 200/实际 130 → 70/35%"的断言——三层闭环，口径才不会在传递中失真。

**洞察**：**规范的敌人是解释空间**。把最容易被做错的口径（算例、幂等、制衡、冻结）写成可执行断言，是把设计立场变成了回归测试。这直接借鉴了 Symphony 的做法：可移植的规范必须自带参考算法与测试矩阵，否则只是愿望清单。

### 3.13 为什么规模化之后，验收权与最终问责仍然归人

**决策**：判定必须记录来源类型（人工 / 策略自动 / Agent 建议）及责任主体，按类型分层统计；策略自动验收是宿主授权行为，如实记录，不得显示或合计为人工验收；人工验收覆盖率是价值报告必附口径。

**原因**：Agent 主导执行后，大量低风险验收必然走向策略自动化——这是对的，堵不住也不该堵。但自动化验收的责任无法落在一个无身份的系统上：出了事故，索赔、审计与监管追问的对象必须是可问责的自然人或法人。若把策略验收混计为"人工验收"，节省率会被虚增，人工被替代的进度也会被谎报。

**洞察**：**吞吐可以交给自动化，责任不能**。产品的诚实做法是让自动化验收作为独立的判定来源被完整记录、分层呈现——管理层既能看到"多少活已经不需要人点头"（真实效率），也能看到"多少结论仍以人的名义承担"（真实风险）。两条曲线一起看，才是数字员工替代进度的真实仪表。

## 4. 刻意不做什么（及产品理由）

| 不做 | 理由 |
| --- | --- |
| 不替代宿主验收 | 见 3.2：拥有权力即失去独立性 |
| 不取消独立复核环节，也不坚持"必须人工执行" | 见 3.4：前者回到自证，后者死于吞吐；正确解是谱系制衡 + 分工收敛 |
| 不允许执行者及其同谱系副本充当独立复核 | 见 3.4：女巫克隆会让"独立性"变成数量游戏 |
| 不把策略自动验收混计为人工验收 | 见 3.13：吞吐可以自动化，责任不能 |
| 不做通用 Agent 编排/执行框架 | 见 3.10：绑定执行层失去治理中立性 |
| 不以自动评分认定业务价值 | 评分与验收的分离是整个体系的地基 |
| 不从 Trace 推断任务完成 | Trace 缺失不应惩罚闭环；证据等级不同不可混用 |
| 不做全企业流程统一 | 首期只打透一个场景；流程统一是结果不是前提 |
| 不承诺分布式调度 | 模块化单体 + 单一调度权威起步，规模由试点测量决定 |
| 不在本期做多租户 SaaS 化 | 信任与合规先在受控部署中验证 |

## 5. 与常见替代方案的差异

| 方案类型 | 它回答的问题 | Outcome 回答的问题 |
| --- | --- | --- |
| APM / Trace 平台 | 系统跑得健不健康 | 交付的业务成果值不值钱 |
| AgentOps / 实验台 | 哪个 prompt/模型分数高 | 分数差异是否可比、可复现、经独立复核 |
| BI 看板 | 指标现在是多少 | 指标的分母、缺失与口径版本是什么 |
| 人工验收台账 | 谁点的通过 | 通过的成果对应多少投入、相对基准省了多少 |
| LLM 评测服务 | 模型输出得几分 | 这个分数能否支撑发布决策与经营结论 |

Outcome 不与上述方案竞争，它消费它们的输出（任务事实、Trace、评分、验收记录），在其上叠加**制衡、冻结与归因**。

## 6. 如何验证这些设计是有效的

产品自身的效果指标（与 ROADMAP 阶段对应）：

1. **可复核率**：任意一份节省报告，能在无人工补数的情况下回溯到任务级证据的比例（目标 100%）。
2. **口径质询通过率**：业务/CFO 方对报告分母、缺失、范围的质询中，系统当场可回答的比例。
3. **改进存活率**：宣称"已验证"的改进，三个月后在线复测仍成立的比例。
4. **复发率**：已关闭质量问题在同范围再次触发的比例（衡量闭环是否真闭环）。
5. **接入工时与首份可信报告时间**：衡量低侵入集成立场是否兑现。

反指标（出现即设计被违反）：出现补零的成本、出现未冻结的"提升"结论、出现同谱系自复核通过的样本、出现未校准复核主体计入独立标签、出现缺失人工核验覆盖率的发布版本、出现无证据引用的"已验证"洞察。

## 7. 边界与诚实声明

- 当前交付是 **v0.1 规范 + 本地原型**，无服务端、无真实集成、无生产认证；原型中的身份切换与评测执行含模拟行为。
- 本文的设计立场在小规模试点中尚未经受多租户、高并发与合规审计的检验；ROADMAP 阶段 2/4 是它们的验证点。
- 借鉴 openai/symphony 的是规范体例与调度/对账/隔离的工程模式；业务语义（验收锚点、制衡、冻结、归因）是 Outcome 自有的领域判断。

## 8. 给评审者的三句话

1. 如果你认同"验收才算数"，那么本规范的成本口径、实验冻结与复核制衡是必然推论，不是过度设计。
